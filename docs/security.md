# Security design

[← README](https://github.com/Dennis-Otto/paperless-unified-search) · [Architecture](architecture.md) · [Roadmap](roadmap.md) · [Releases](releases.md)

What Paperless Unified Search protects, what it trusts and which risks remain. [SECURITY.md](https://github.com/Dennis-Otto/paperless-unified-search/blob/main/SECURITY.md) says how to report a vulnerability and how to verify a release, and argues why the repository and its releases are safe.

## What you can expect

- Only administrators of Nextcloud can see and change the settings of the app. Users change only their own choices of *Always search my Paperless documents* and *Notify me about new documents* in their personal settings, and only while the administrators let them. Every request passes Nextcloud's login and its CSRF check, and saving and *Disconnect* ask for the password when it wasn't confirmed in the last 30 minutes.
- The Paperless API token is stored in Nextcloud's credentials manager and goes only to the Paperless server it was saved for: no response, page or message of the app contains it, and a URL with another scheme, host or port needs the token entered again ([decision 0003](decisions/0003-bind-the-token-to-its-server.md)).
- `occ paperless_unified_search:setup` takes the token only from its standard input or from an environment variable, never from an argument, which the history of the shell and the list of processes would show to other users of the server; no output of occ contains it.
- A stored token that can't be decrypted, as after a move of Nextcloud with another secret in `config.php`, counts as none: the settings ask for it again, and the search shows no Paperless documents instead of failing.
- Nextcloud's protection against addresses of the local network stays on. *Paperless runs in my local network* lifts it only for the requests of this app to the Paperless URL of the settings, which then follow no redirect, never for another app or another address, and only an administrator who confirmed the password can select it ([decision 0004](decisions/0004-local-network-opt-in.md)).
- A Paperless document appears in the results of a user only when that user can open a file of the archive account whose name carries its marker `[P<ID>]`: their own if they are that account, or one it shared with them. A file that only carries the marker in its name stands for no document. Selecting the result opens that file in Nextcloud.
- Search terms reach Paperless only when the user switches on *Search connected services*, picks *Paperless documents* in the smart picker, chose *Always search my Paperless documents* in the personal settings, saved them for *Notify me about new documents* there, when an administrator has marked Paperless as trusted, or when a client of the user, such as a script, asks for this search by its ID through Nextcloud's OCS search API. They travel from server to server, never from the browser to Paperless.
- In the smart picker of Talk, Text, Deck and Mail, a term reaches Paperless only after the user chose *Paperless documents* in it, a choice as explicit as switching on *Search connected services*. The picker searches through the same search provider, with the same rules of who sees which document.
- The link that the smart picker inserts is the link of the synchronized file in Nextcloud, and the app resolves no link itself: Nextcloud renders it with the permissions of whoever reads it, as the preview of the file for a reader who can open it and as the bare link for anyone else.
- The app asks Paperless only for the fields that a result shows: the ID, the title, the date, the correspondent, the type and the tags of a document, and the excerpt around the term, and for the names of the correspondents, the types and the tags of the documents that the user can open. The whole OCR text, the notes and the permissions of the documents never reach Nextcloud.
- Nextcloud's distributed cache keeps the names of correspondents, types and tags for ten minutes, by the server and the ID, for all users, as they come with the token of the app; a result shows a name only for a document whose file the user can open.
- The dashboard widget *New in Paperless* follows the rule of the search: it shows a user only the newest documents whose file of the archive account the user can open. Nextcloud's distributed cache keeps the newest 25 documents for a minute for all users, as they come with the token of the app, with their IDs, titles, the moments that Paperless added them and the IDs of their correspondents, types and tags, never their text.
- The notifications about new documents follow the rule of the search as well: a user hears about a document, and gets its title and a link to its file, only when the user can open its file of the archive account as the notification goes out. Whoever saved the same search and can't open the file hears nothing ([decision 0011](decisions/0011-notify-about-new-documents-when-their-files-arrive.md)).
- The saved searches of a user are stored with their account, up to 10 of up to 500 characters each, only while the user asks for them, and Nextcloud deletes them with the account. A background job sends them to Paperless, with the token of the app, which the personal settings say above the field: saving them is the consent of the user. They reach neither the log nor the history of the problems of the search, and nobody but the user and the administrators of Nextcloud can read them, the latter with `occ user:setting`.
- Requests to Paperless go through Nextcloud's HTTP client, which checks TLS certificates.
- *Try a search* in the settings shows an administrator which Paperless documents a user finds for a term and why the others don't show to them, by their IDs, titles and tags alone: no content, no excerpt, no file and no account that owns one. Like every route of the settings, only administrators can call it, and the audit log of the app *Auditing / Logging* (`admin_audit`) records which administrator tried a search as which user, whatever the log level, as does the log of Nextcloud at level info, without the term.
- A failed search is logged with the kind of error only, without the term, the URL or the token. The history of the administration settings shows it with its message as well, as it shows a request that only its second try answered; the message loses the token, the term in any case, also of letters beyond ASCII such as `Ä` and `ä`, and the query of every URL first.
- What a user types can't fill the history of the problems of the search: a query or a page that Paperless refuses, as one still being typed, finds nothing and writes nothing, and the problems of one kind write the history at most once in 30 seconds ([decision 0006](decisions/0006-retry-only-before-a-connection.md)).

## What is protected

| Asset | Where it lives | Protection |
| --- | --- | --- |
| The Paperless API token | Nextcloud's credentials manager | Stored only there; the settings carry only whether a token is configured; saving without a new token keeps the stored one, but only for the server it was saved for |
| The search terms of the users | Sent to Paperless | Only when the user asks for it, in the search or through the API, or an administrator trusts Paperless; never logged by the app; removed from the messages of the history of the diagnostics, as is the query of every URL |
| Documents in Paperless | Paperless | Read through a dedicated account with read access only, which every test of the connection checks: the settings, `occ` and the overview warn about the token of a superuser or an admin, or of an account that may add, change or delete documents, or add or change users or change groups, which lets it grant itself that; shown only through a file of the archive account that the user can read; *Try a search* shows administrators the IDs, titles and tags of the documents that a user finds, nothing more, and logs who looked as whom |
| The configuration | Nextcloud's app configuration | Changed only by administrators who confirmed their password in the last 30 minutes, after a test of the connection |
| The services of the local network | Behind the firewall of Nextcloud | Nextcloud refuses their addresses to every request; the app asks for an exception only for the Paperless URL of the settings, when an administrator selected *Paperless runs in my local network*, and follows no redirect then |

## Trust boundaries

<picture>
  <source media="(prefers-color-scheme: dark)" srcset="images/diagrams/the-trust-boundaries.dark.svg">
  <img src="images/diagrams/the-trust-boundaries.svg" alt="The trust boundaries: Four boundaries meet at Paperless Unified Search on the Nextcloud server. 1, the browser of an administrator sends the settings. 2, the unified search or the smart picker of a user sends the term and the page. 3, the app sends the term and the token to Paperless-ngx outside the server and gets an untrusted answer. 4, the app looks into the folders of the user for files of the archive account. The token stays in the credentials manager of the server.">
</picture>

1. **Browser → app.** The routes of the settings page pass Nextcloud's login, its CSRF check and the check of the administrator, and saving and *Disconnect* its password confirmation. The URL must use `http` or `https`, name a host, an IPv4 address or an IPv6 address in brackets, and carry no credentials, query or fragment; an internationalized name is stored in punycode. A blank token keeps the stored one only for a URL with the scheme, host and port of the stored URL; the archive account must exist and is stored as Nextcloud spells its ID.
2. **Nextcloud's search → app.** The term and the cursor of a page come from the user, through the unified search or the smart picker: the cursor must be a whole number, the offset of a hit, and a search pages through the first 10,000 hits; a page holds at most 50 results, and one search asks Paperless for at most 4 pages of 25 hits.
3. **App → Paperless.** Nextcloud's HTTP client refuses addresses of the local network unless *Paperless runs in my local network* is selected; then the request reaches the Paperless URL of the settings and follows no redirect. The request names the fields of the documents to send, so that the OCR text stays in Paperless. Every answer is untrusted input. It must be JSON with a list of results; a document without a numeric ID is left out; titles, dates and the names of correspondents, types and tags are used only when they are text, and a date is formatted only when it is a day that exists, as is the moment that Paperless added a document; the excerpt loses the tags of Paperless before its entities become characters again, is cut to 180 characters, and, with the rest of the line below the title, gets a space after every `<` that would start a tag, so that this line holds no HTML tag whatever the document says. The answer of `/api/ui_settings/` decides only the warnings about the account of the token: one other than HTTP 200 with JSON that names the user and its permissions leaves them unknown, and the test of the connection passes as before.
4. **App → files of Nextcloud.** The file locator searches only the folders of the searching user, with Nextcloud's permissions, and takes only files, never folders, and only those that the archive account owns, with the exact marker of a document in their name. The marker in a name is chosen by whoever names the file and proves nothing by itself; the files of the archive account reach other users only through its shares.

## Residual risks

- A link of the smart picker carries the ID of the file in Nextcloud. A reader who can't open the file sees that number, but neither its name nor its content.
- An administrator can learn with *Try a search* which document titles a user can see, for any term and any user. The answer holds the titles and tags alone, and the audit log names the administrator and the user, if the app *Auditing / Logging* is enabled (otherwise only the log of Nextcloud does, at level info or lower); an administrator of Nextcloud can see far more anyway, for example by signing in as the user. A hoster who doesn't want this should not make the operators of an instance its administrators.
- The marker `[P<ID>]` ties a file of the archive account to a document, and the search judges the permissions of the searching user. Whoever may write into a folder of the archive account, through a share with write permission or a public link that allows uploads, finds none of the documents in it, also not through another share that reaches the same file read-only, but can still put a file with the marker of any document there for the others who may read that folder, and a file that stays behind once a share is read-only again counts for every reader. So does a file that leaves the folder with write permission for one that its writer may only read: [Paperless Sync](https://github.com/Dennis-Otto/paperless-sync) moves an inbox file that Paperless refuses into its error folder and keeps its name, so a broken upload named `x [P999].pdf` counts as document 999 there for every reader of the base folder, its writer as well. The settings, `occ paperless_unified_search:check` and the overview warn about each share that allows changes: share the archive read-only.
- The permissions of the Paperless account decide which documents the search can find. Use a dedicated account with only the read permissions that the search needs, as the [README](https://github.com/Dennis-Otto/paperless-unified-search#configuration) describes. The test of the connection warns about an account that may do more, but only when the account may view its UI settings, and only as the account was at the time of the test: a permission granted later shows at the next test, such as `occ paperless_unified_search:check` in a scheduled job.
- With *Always include Paperless in global search* on, every search term of every user reaches Paperless. Turn it on only for a Paperless server that you trust as much as Nextcloud.
- Every search term of a user who chose *Always search my Paperless documents* reaches Paperless, as the hint of the checkbox says; nobody can choose it for another user. Turn off *Let users include Paperless in all their searches* to keep every term that the switch doesn't send away from Paperless; the search then ignores the stored choices ([decision 0008](decisions/0008-let-each-user-always-search-paperless.md)).
- A notification keeps the title and the path of a file that the user could open as it went out. Taking back the share later closes the file, but not what the notification already says, as with a mail about the file. Paperless sees the saved searches of all users under the one account of the token, so its logs can't tell whose search it is, and an administrator of Paperless can read them there. The titles of the documents that wait for their files, at most 200 and also of those that nobody in Nextcloud may open, stay in the app configuration of Nextcloud for up to two days; *Disconnect* deletes them.
- An `http` URL is allowed, for a Paperless in a trusted local network; then the token and the search terms travel unencrypted. Use `https` whenever the connection leaves such a network.
- Within 30 minutes of a confirmed password, whoever takes over the session of an administrator can still change the settings, for example to a server of their own with a token of that server, which then receives the search terms. They can't collect the stored token this way. Nextcloud's own settings carry the same risk; sign out of shared browsers.
- With *Paperless runs in my local network* selected, an administrator, or whoever takes over their session within 30 minutes of a confirmed password, can point the test of the connection at any address and port of the network, with a token of their own, and learn from its result and from how long it takes whether a service listens there, and whether it answers as Paperless does. The request has the path of the Paperless API and follows no redirect; of the answer, the settings show only the kind of failure, such as a host that doesn't resolve, a refused token, a status of HTTP or an answer that isn't the one of Paperless, never its content, and the stored token never goes there. An administrator of Nextcloud can do more than that anyway, for example by installing an app.
- A blank token keeps the stored one for another path of the same server, so an application that the same scheme, host and port serve under another path receives it once an administrator enters that path.
