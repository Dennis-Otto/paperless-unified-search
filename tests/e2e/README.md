# Docker end-to-end tests

The suite starts Nextcloud with this checkout mounted read-only as a Custom App: `run.sh` the image of `compose.yaml` (set `NEXTCLOUD_IMAGE` to choose another, such as `nextcloud:35-apache`), [`run-all.sh`](#every-supported-version-at-once) and the CI the current release of every version from `min-version` to `max-version` in `appinfo/info.xml` at the same time, and every week also [the coming Nextcloud](#the-coming-nextcloud). A deterministic local HTTP service emulates the small Paperless API surface used by the app. Like Paperless, it sends only the fields of the documents that a request names, and the excerpt of a search with them; unlike Paperless, it answers a request that names none with HTTP 400, so that the suite fails as soon as the app would make Paperless send the whole OCR text of every document. Like Paperless, it answers in pages, of 25 documents unless a request asks for another size, with the absolute link to the next page, and refuses a page past the last one with HTTP 404. A list without a search holds every document of the mock, those of the search for `mobiletest` and those of the demo of the screenshots, each with the moment that Paperless added it, and like Paperless the mock orders a list by the field of `ordering`, newest first with a minus, as the dashboard asks for `ordering=-added`; unlike Paperless, which ignores a field that it can't order by, it refuses one with HTTP 400. Like Paperless-ngx 3.3.0, it names its version in the headers `X-Version` and `X-Api-Version` of every answer to the token, refuses a query of its advanced syntax with a range of dates that is still being typed, such as `created:[2026 to`, with HTTP 400 and the errors of the field `query`, and searches the words of any input in the simple mode of its search, the parameter `text`. Like Paperless, it marks up the words of the term in the excerpt with `<b>` and writes the characters of HTML as entities, such as `&#x27;` and `&quot;`, which the result has to show as text again, and it lists its correspondents, types of documents and tags by the IDs of `id__in`, with every field of each, as Paperless-ngx 3.3.0 does. Like Paperless, it answers `/api/ui_settings/` with the user of the token and the permissions of its account: its token `e2e-only-token` belongs to an account that may view documents, correspondents, document types, tags and its UI settings, the account that the documentation recommends, and it also takes `e2e-superuser-token`, the token of a superuser. And as Paperless or its network sometimes does, it fails: with HTTP 500 for the term `e2e-error`, and for `e2e-drop` it breaks off the connection of the first request without an answer. Whether real Paperless-ngx answers as the mock does, [the contract tests](#against-a-real-paperless-ngx) check every week.

The search for `pagetest` checks how the app fills a page of results: the mock ranks 40 documents for it, more than a page of the app's requests to Paperless, and the archive account shares a folder with the files of seven of them, none of the first 19, with `e2e-other`, and keeps one more file to itself. The first page of 5 results takes its documents from both pages of Paperless, and the next page, from the cursor of the first, holds the remaining two, without repeating or leaving out a document.

The date filter of the search reaches Paperless as `created__date__gte` and `created__date__lte`, which the mock filters its documents by, as Paperless does, refusing a value that is no day `YYYY-MM-DD` with HTTP 400. The list of the search providers names `since` and `until` for the app, without which Nextcloud's web search would send it no date filter. For `e2e-user` in Berlin, a search for `mobiletest` since 22:00 UTC on August 26 finds nothing, as that is already August 27 there, after the document of August 26, and one until 22:30 UTC on August 25 finds it, as that is August 26; in UTC, each would find the answer of the other.

Each result of `mobiletest` shows what the document is, and the suite checks it in the answer of the search for the browser, iOS and Android: the line below the title holds the date of the document in the language of the user, *Aug 26, 2026* in English, *26.08.2026* for `e2e-user` set to German and *26 août 2026* for `e2e-user` set to French, where the search also names its results *Paperless-Dokumente* and *Documents Paperless*, its correspondent, its type and its tag *paid*, which the app asks the mock for, without the tag of the inbox, which the document has as well, and the excerpt as text without a tag, `O'Brien & "Sons" < GmbH>` from `&lt;GmbH&gt;`. `run.sh` lets Nextcloud draw previews of PDF files, as an administrator may: the result links the preview of its file, which answers `e2e-user` with an image, here the icon of PDF files, since the image of Nextcloud has no Ghostscript, and `e2e-other`, who can't open the file, with HTTP 404, and has no icon, which the smart picker would show in place of the preview.

Besides the search, the suite checks the smart picker: it lists *Paperless documents* with the search provider and the icon of the app, and Nextcloud renders the link of a result as the file for the archive account and for a user the file was shared with, and as the bare link, without the name of the file, for a user who can't open it. It checks the guarantees of the settings as well: every route of the settings answers a user who isn't an administrator with HTTP 403 and a request without a login with 401, and leaves the settings as they are; a save with a blank token for another server answers 400 and sends that server nothing, which the log of the mock shows, as it answers as `other-host` too; a save with a token that the mock refuses answers 400 with the code `unauthorized` and a message in the language of the administrator, German, and leaves the settings as they are; the settings page speaks German to an administrator set to `de` and formal German to one set to `de_DE`, *Deutsch (Förmlich: Sie)*; an archive account typed in another case is stored as Nextcloud spells it; and the answer of a save names the version of Paperless that the test of the connection found.

The suite sets the app up through occ, as an administrator's script does: `occ paperless_unified_search:setup` gets the token from its standard input, saves the settings once the mock answers, and says so without the token, and `occ paperless_unified_search:test` exits with 0. The settings route is then tested for what only it does, such as the refusals for users who aren't administrators. Before and after the archive account shares the file of document 123 with `e2e-other`, `occ paperless_unified_search:search e2e-other mobiletest --explain --json` names its verdict, *not shared* and then *shown*, and *no file* for document 999, which `assert_occ.py` checks. *Try a search* of the settings page, `POST /settings/try`, gives an administrator the same verdicts for `e2e-other` before and after the share, which the mode `try` of `assert_occ.py` checks, and fails the suite when its answer holds anything beyond the ID, the title and the verdict of each document; it answers an account that doesn't exist with HTTP 400 and the code `unknown_user`, a user who isn't an administrator with 403 and a request without a login with 401. `occ paperless_unified_search:check` then counts 1 of the 7 documents of the mock with a file, from the field `all` that the mock adds to every list as Paperless-ngx does, and says that the account of the token may change no document and may view correspondents, types and tags, which the mode `token` of `assert_occ.py` checks. With the token of a superuser, `setup` saves with a warning, `check` names the warning and `occ setupchecks` shows it, before the suite goes back to the token of the mock. Next, the archive account shares its folder `Base` with `e2e-writer` read-only and the folder `Inbox` in it with write permission, as Paperless Sync lays out its base folder, and `e2e-writer` names a file in `Inbox` `Forged [P999].txt`, which it reaches through both shares: the search finds nothing for `e2e-writer`, `--explain` and *Try a search* name document 999 *writable*, `e2e-other` still finds 123 in its share that allows only reading, and `occ paperless_unified_search:check` and `occ setupchecks` warn about the share, which the modes `shares` and `setupcheck` of `assert_occ.py` check; once the shares and the file are gone, both say that the archive is shared read-only with 1 user. Once the archive account no longer exists, `occ setupchecks` shows the warning of the app with its link to the settings.

Right after enabling the app, the suite stores `last_failure` and `last_recovery`, the last failed search that version 0.3.0 kept, as lazy values the way 0.3.0 stored them, and runs `occ maintenance:repair`, which runs the repair step of the app as every update of it does: the step names itself in the output, and `occ config:app:get` finds neither key afterwards.

The dashboard offers the widget *New in Paperless* only once the app is set up: before `occ paperless_unified_search:setup`, `GET /ocs/v2.php/apps/dashboard/api/v1/widgets` lists no such widget, and afterwards it does, with its dark icon as an absolute URL and items of version 2 of the API, and for `e2e-other` with the link *Files shared with you*, which answers `e2e-other` with HTTP 200, while `e2e-user`, the archive account, gets none. `GET /ocs/v2.php/apps/dashboard/api/v2/widget-items` then lists *Mobile viewer test* for `e2e-user`, with the day that the mock added it, its correspondent, its type and its tag, the link and the preview of its file, and as its `sinceId` the moment that the mock added it, but not document 999, which the mock added later and no file stands for; `e2e-other` gets no item and the message *None of the newest Paperless documents has a file that you can open.* before the share of the file of 123, and the document right after it. Three requests for the items of the widget, by both users, cost the mock one request for its newest documents, which its log counts. Set to French, `e2e-other` gets the widget *Nouveau dans Paperless* with the link *Fichiers partagés avec vous* and the message in French. `assert_dashboard.py` checks each answer.

The suite makes the search fail, too, and checks the history of its problems that the administration settings show under *Search problems*, which Nextcloud keeps in its configuration of the apps. Before that, a search for `mobiletest created:[2026 to`, which the mock refuses in the advanced syntax, shows the document of its word from the simple mode, and a search for `pagetest` from a cursor past its last page finds nothing; neither may count in the history, which then holds only the two problems that follow. A search for `e2e-error` shows no documents and goes into the history as a failed search, with the message *Paperless returned HTTP 500.*; a search for `e2e-drop` shows its document from the second try of the request, which goes into the history as well, with the message of the HTTP client, and shows that searches work again. `assert_history.py` reads the page that Nextcloud renders: neither term appears on it, nor the token, nor the query of the URL that the message of the HTTP client repeats. The browser then clears the history with *Clear history*, after which the page says *No problem recorded.*.

Run:

```bash
bash tests/e2e/run.sh       # one version: the image of compose.yaml
bash tests/e2e/run-all.sh   # every supported version at the same time, as the CI does
```

Optional environment variables:

- `E2E_PORT`: host port for Nextcloud, default `18082`
- `DOCKER_BIN`: Docker CLI path, default `docker`
- `E2E_PROJECT_NAME`: Compose project name, default `paperless_unified_search_e2e`
- `NEXTCLOUD_IMAGE`: the image of Nextcloud, default the release that `compose.yaml` pins
- `KEEP_E2E=1`: keep containers and the test volume running after the suite
- `E2E_IGNORE_MAX_VERSION=1`: enable the app with `--force` on a Nextcloud newer than `max-version`, as `canary.sh` does
- `E2E_SKIP_PLAYWRIGHT_PULL=1`: leave the download of the image of Playwright to the caller, as `run-all.sh` does

`run.sh` downloads the image of Playwright in the background while Nextcloud sets itself up, removes the containers without waiting for them to stop (and leaves them on a runner of GitHub, which is thrown away after the job anyway), and turns off Nextcloud's password policy, which would check every new password against [Have I Been Pwned](https://haveibeenpwned.com/Passwords), so that no test depends on a service outside the machine. Each call of `occ` starts PHP and Nextcloud anew, which takes a few seconds while three versions run at once; so `occ` only installs Nextcloud, trusts its name in the network and enables the app, and the running web server turns off the password policy and creates the users. The web server has to do that itself: it caches the settings of the apps for three seconds and would go on checking passwords right after `occ` turned the policy off. Nextcloud keeps `allow_local_remote_servers` off, as a fresh installation does: the app reaches the mock at its address in the network of the project only through its own switch **Paperless runs in my local network**, which the tests turn on when they save the settings, after a save without it that Nextcloud refuses before any request reaches the mock.

The suite checks what reached Paperless in the journal of the mock, not in the log of Docker: `mock_server.py` writes each request that it answers, with the status of its answer, into `/tmp/requests.log` of its container before the answer leaves, so a check right after an answer of Nextcloud finds the request there, such as the date filter of a search, the two saves with a token or the one request of the dashboards of a minute. Docker copies the output of the container into its log a moment later, so `docker compose logs` may still lack the last request. `run.sh` reads the journal into a variable and searches that: piped into `grep --quiet`, which stops reading at its first match, `docker compose logs` died of SIGPIPE while it wrote the rest, and `set -o pipefail` failed the check of the date filter now and then although the request had arrived ([#94](https://github.com/Dennis-Otto/paperless-unified-search/issues/94)). `selftest.sh` reads the journal of the mock right after each answer and fails on a pipe into `grep --quiet` in a script of the suite.

All credentials and document data are synthetic, local to the disposable Compose project, and intentionally unsuitable for production.

## The log of Nextcloud

At its end, `run.sh` pipes the log of Nextcloud, `data/nextcloud.log`, into `assert_log.py`, which fails on every record of the app that no test expects. A record is of the app when the app wrote it, or when its message, its exception or its data names a file of the app, `custom_apps/paperless_unified_search/`, or its namespace, `OCA\PaperlessUnifiedSearch\`. Nextcloud logs an uncaught exception for the app `index`, `core`, `PHP` or `no app in context`, with a trace through `lib/`, so a `TypeError` in the search provider, the dashboard widget, the smart picker or a command of occ counts as well; the URL of a request to a route of the app doesn't, as it names the app whatever code failed ([#237](https://github.com/Dennis-Otto/paperless-unified-search/issues/237)).

| Finding | What the log holds | How to fix it |
| --- | --- | --- |
| *a deprecation of PHP*, *a notice of PHP* or *a warning of PHP in a file of the app* | PHP raised it in a file of the app, at any level, such as a parameter that is nullable without saying so | Change the code at the place that the finding names, as the migration guide of that version of PHP says |
| *an error of the app* or *a fatal error of the app* | A record of the app at the level error or fatal, such as an uncaught exception with a trace through `lib/` | Fix the code at the place that the finding names, the first frame of the trace in the files of the app |
| *a warning of the app that no test expects* | A warning of the app that `EXPECTED_WARNINGS` of `assert_log.py` doesn't name | Fix its cause. A warning that a step of `run.sh` provokes on purpose, such as the save of a token that the mock refuses, goes into `EXPECTED_WARNINGS`, with that step |

The images of Nextcloud run a newer PHP than the unit tests, PHP 8.4 for Nextcloud 33 and PHP 8.5 for 34 and 35, against 8.2 and 8.3 of the unit tests, so these tests are the only ones that see what the newer PHP deprecates; the next major version of PHP turns many deprecations into errors. Nextcloud logs a deprecation of PHP at debug and a notice at info, below its default log level, warning, so `run.sh` sets the condition `log.condition` of `config.php`, which logs every record of PHP and of the app at debug. The log level debug for all would do the same, with a trace for each query of the database that reads a table which the request wrote: 100 MB within the first minute. `run.sh` fails as well when PHP of the image doesn't hand Nextcloud every error, `error_reporting` other than `E_ALL`, as `php.ini-production` would leave out the deprecations.

The check first prints how many records the log holds at each level, of all and of the app, so that a log that grows shows in the output of the job, and how often each expected warning came. Each finding follows with what it is, the app that the record names and its message, its place in the files of the app, the request or the command of occ during which Nextcloud wrote it, and the record in JSON, with a line for each frame of its trace in place of the frame with its arguments:

```text
- an error of the app, for the app 'index': Argument #1 ($term) must be of type string, null given
  at lib/Search/PaperlessSearchProvider.php:42, during GET /ocs/v2.php/search/providers/paperless_unified_search/search
  {"app": "index", "exception": {"Exception": "TypeError", ...}, "level": 3, ...}
```

`KEEP_E2E=1` leaves the containers running, and `docker compose --project-name paperless_unified_search_e2e exec nextcloud cat data/nextcloud.log` shows the whole log, with the project `pus_e2e_<version>` for a version of `run-all.sh`. `selftest.sh` tests `assert_log.py` with records of its own, as Nextcloud writes them.

## Every supported version at once

`run-all.sh` reads `min-version` and `max-version` of `appinfo/info.xml` and starts `run.sh` for every major version from the one to the other at the same time, each with the image `nextcloud:<version>-apache`, the Compose project `pus_e2e_<version>` and the port `18000 + <version>`, such as `18035` for Nextcloud 35. Each version writes its log to a file of its own; the script notes each version as it finishes and then prints the logs one after another, in the CI each in a group named after the version and its result. The script fails when one version does, and Ctrl-C stops every version and removes its containers. A version that takes longer than `E2E_VERSION_TIMEOUT` seconds, 600 by default and more than twice what it needs, stops and fails as well, with its log up to that point and the state of its containers, long before the job of the CI times out.

```bash
bash tests/e2e/run-all.sh                       # every version from min-version to max-version
E2E_VERSIONS="33 35" bash tests/e2e/run-all.sh  # only Nextcloud 33 and 35
E2E_PHONE=newest bash tests/e2e/run-all.sh      # the phone in the search dialog only with the newest version
E2E_UPGRADE=newest bash tests/e2e/run-all.sh    # the upgrade from the last release only with the newest version
```

`E2E_PHONE` decides where [the search dialog](#the-search-dialog) runs on a phone: `all`, the default, with every version, and `newest` only with the newest of the versions, while the others run it on a laptop alone, which saves each of them 16 to 19 seconds on a runner of GitHub. The CI sets `newest` for a pull request; see [In the CI](#in-the-ci). `run-all.sh` hands each version its sizes as `E2E_FLOW_SIZES`, such as `laptop`, which `run.sh` passes to `flow.mjs`, and the summary of the run lists them in its column *Search dialog*.

`E2E_UPGRADE` decides with which versions [the upgrade from the last release](#the-upgrade-from-the-last-release) runs beside `run.sh`, at the same time, each in the Compose project `pus_upgrade_<version>` on the port `19000 + <version>`: `all`, the default, with every version, `newest` only with the newest of them, as the CI sets for a pull request, and `none` with no version. A version passes only when its tests and its upgrade pass; its upgrade has a group of its own in the log, *Upgrade on Nextcloud 35 (passed, 95 s)*, and the time limit of `E2E_VERSION_TIMEOUT` as well. The summary of the run shows the result of each upgrade and the release that it started from in its column *Upgrade*, and the output `failed` names a version whose upgrade broke as *Nextcloud 35 (35.0.1, upgrade failed)*.

On a runner of GitHub, with four CPUs and 16 GB of memory, three versions at once take about three to four minutes, much of it in the checks in Chromium, as three browsers and three Nextclouds share the CPUs. The script first downloads the images of Nextcloud and of the mock for every version, and the image of Playwright only while Nextcloud sets itself up, which is faster than downloading them all at once. The upgrade needs no browser and ends in about two minutes, long before the tests of its version; it makes them less than a minute slower, about 35 seconds for Nextcloud 35 on a laptop, the time of the CPUs that its Nextcloud takes from them.

## The upgrade from the last release

`run.sh` enables the checkout in a fresh Nextcloud, so it never sees what changes only on an update: a key of a setting that the app renames, the token in the credentials manager, a value that becomes lazy, the archive account, the switch for the local network or a new repair step. A mistake there would reach every installation with the next release, whose users would then find *Paperless is not configured* or an empty search. `upgrade.sh` makes the update that an administrator's Nextcloud makes when the App Store brings the next version:

  <img src="../../docs/images/diagrams/the-upgrade-from-the-last-release.svg" alt="The upgrade from the last release: upgrade.sh asks GitHub for the last release of the app; without one, it skips the test with a notice. It installs the release into a fresh Nextcloud, sets it up with occ and searches; package.sh packs the checkout as krankerl packs a release, with the next version. The package replaces the release, and occ upgrade runs each repair step of the app once. The test passes when the settings page shows the same settings, the app keeps every key, the same search finds the same file with the stored token, which still goes to its own server alone, and the log of Nextcloud holds no finding; otherwise it fails with what the upgrade lost.">
</picture>

1. **The release.** It asks GitHub for the last release of the repository that `appinfo/info.xml` names, through the redirect of `/releases/latest`, without the API and its rate limit, and downloads `paperless_unified_search.tar.gz`, the package of the App Store. Before Docker starts, `openssl` checks its signature `.sig` with the certificate of the app at the App Store, as Nextcloud checks an update from there, and, where `gh` is installed, `gh attestation verify` its signed provenance `provenance.sigstore.json` from the isolated build, `build-release.yml`, without a login. A repository without a release yet skips the test with a notice; any other answer of GitHub, such as a 429, fails it. It skips as well when the `<nextcloud min-version max-version>` of the release leaves out the version of Nextcloud under test, since `occ app:enable` would refuse the release: the pull request of the upstream bot that raises `max-version` to a new Nextcloud passes there without the upgrade, which runs again once a release supports it.
2. **The package.** `package.sh` packs the checkout as `krankerl package` of `build-release.yml` packs a release: the files that Git tracks, without what each `.nextcloudignore` leaves out, which Git itself reads as krankerl does, for the folder of the file and every folder below it. For v1.1.1, that is the same 57 files as the release, which only adds `appinfo/signature.json`, the signature of the App Store. The package takes the files as the checkout has them, with the changes that are not committed yet, so a file that a `.nextcloudignore` leaves out by mistake, such as a class of `lib/`, is missing from the app as it would be after an update from the App Store. Nextcloud upgrades an app only to a newer version: while the checkout names the version of the release, as it does until the release bot raises it, the package names the next patch version, such as 1.1.2 after 1.1.1.
3. **The release, set up.** A fresh Nextcloud of `compose.yaml`, with the mock of Paperless and the checkout out of the way in `/opt/checkout`, gets the release in `custom_apps`, as the App Store installs it, and `occ paperless_unified_search:setup` sets it up with the token from its standard input, the archive account `e2e-user`, the switch for the local network and the global search, every setting other than its default, so that one that the upgrade resets shows. It stores the last failed search of version 0.3.0 as well, which the repair step of the app removes, and searches as `e2e-user` for `mobiletest`, which finds the file of document 123.
4. **The upgrade.** The package replaces the release, and `occ upgrade --verbose` has to name the new version, run each repair step of the app once, between *Updating <paperless_unified_search> ...* and *Updated <paperless_unified_search> to 1.1.2*, and the one that removes the keys of version 0.3.0 among them, without a warning or an error of a repair step of the app. The App Store resets the cache of the compiled PHP code in the process that installs an update; `occ` runs apart from the web server, which therefore starts new processes, as otherwise it would mix the classes of the release that it holds with the new files for up to a minute.
5. **What it keeps.** The page of the administration settings shows the same URL, archive account, switches and stored token as before, read by the app as it reads them, so that a renamed key shows as an empty field; `occ config:list` still names every key of the app but those that `RETIRED_KEYS` of `upgrade.sh` lists, the two of version 0.3.0; and the same search finds the same file, with the stored token, which the credentials manager still decrypts. The token still goes to its own server alone ([decision 0003](../../docs/decisions/0003-bind-the-token-to-its-server.md)): `occ paperless_unified_search:setup --url=http://other-host:8080` without a token is refused and asks for the token, and the journal of the mock holds no request of it. Last, `assert_log.py` checks the log of Nextcloud from the upgrade on.

```bash
bash tests/e2e/upgrade.sh                                         # the image of compose.yaml
NEXTCLOUD_IMAGE=nextcloud:35-apache bash tests/e2e/upgrade.sh     # another version of Nextcloud
E2E_UPGRADE_FROM=v1.0.0 bash tests/e2e/upgrade.sh                 # from an older release
```

`upgrade.sh` takes `E2E_PORT`, default `18182`, `E2E_PROJECT_NAME`, default `paperless_unified_search_upgrade`, `NEXTCLOUD_IMAGE`, `DOCKER_BIN` and `KEEP_E2E=1` as `run.sh` does, and `E2E_UPGRADE_FROM` names the tag of the release to start from in place of the last one. A key that a change retires on purpose needs a repair step that removes it and its place in `RETIRED_KEYS`. `assert_upgrade.py` turns the answer of the search, the page of the settings and the keys into the lines that the script compares, and `selftest.sh` tests it, `package.sh` in a repository of its own and `upgrade.sh` up to the start of Nextcloud with fakes of `curl`, `gh` and Docker and a release that it signs itself: a signature that doesn't match, a certificate of another app, a refused provenance and a release without one stop the script before Docker starts.

## In the CI

The workflow *Docker E2E* (`.github/workflows/e2e.yml`) runs `run-all.sh` in one job, the required check `nextcloud`. A pull request or a push to `main` that changes no file the tests cover passes the check in seconds without running them, with a notice that says so; the job stays and passes, so that the required check reports success. `scope.sh` decides it, and `selftest.sh`, which `scripts/check.sh` runs, tests it with real merge commits and pushes in throwaway Git repositories, `run-all.sh` with a fake Docker, and the journal of the mock with requests of its own. The tests cover:

- the app: `appinfo/`, `lib/`, `templates/`, `js/`, `css/`, `img/` and `l10n/`
- `composer.json` and `composer.lock`
- `.nextcloudignore` and `krankerl.toml`, which decide what the package of the upgrade test holds
- the tests themselves, `tests/e2e/`
- the workflow `.github/workflows/e2e.yml`

In a pull request, the search dialog runs on a phone only with the newest supported Nextcloud (`E2E_PHONE=newest`), and on a laptop with every version: a layout of the phone that breaks with every version still fails the pull request, and the required check takes about 16 to 19 seconds less for each other version ([#108](https://github.com/Dennis-Otto/paperless-unified-search/issues/108)). A push to `main`, the weekly run and a run started by hand test every size with every version, so a break that only an older version shows on a phone fails `main` at the latest, before a release. In the same way, a pull request runs [the upgrade from the last release](#the-upgrade-from-the-last-release) only with the newest supported Nextcloud (`E2E_UPGRADE=newest`), beside its tests, and a push to `main`, the weekly run and a run started by hand with every version ([#242](https://github.com/Dennis-Otto/paperless-unified-search/issues/242)).

The weekly run on Mondays and a run started by hand always test every version, so that the newest release behind each image `nextcloud:<version>-apache` is tested even in a week without a change of the app. When such a run on `main` fails, the job *issue about the supported Nextcloud* opens the issue *A supported Nextcloud release breaks the app* with a link to the run and the versions that broke, each with the release behind its image and its result, such as *Nextcloud 35 (35.0.1, failed)*, which `run-all.sh` writes into the output `failed` of its step, and the command `E2E_VERSIONS="<versions>" bash tests/e2e/run-all.sh` for just these versions from its output `versions`. A weekly run that reaches the time limit of the job, which GitHub reports as cancelled, opens the issue too. The job adds every further failed run to the issue and closes it once the tests pass again against every version, also when the flaky-test bot runs the failed check once more and it passes then. A pull request or a push never touches the issue; there a version that breaks fails the required check. `selftest.sh` runs the script of the job with a fake `gh`.

## Accessibility

At the end of the suite, `accessibility.mjs` checks the administration settings of the app in Chromium with [axe-core](https://github.com/dequelabs/axe-core) against WCAG 2.1 at levels A and AA, in the light and the dark theme of Nextcloud, in five states: with the problems of the search that `run.sh` caused, in the tables of *Search problems*, and the warning about an archive account that doesn't exist, which `run.sh` stores before, on a laptop, 1280 × 900 pixels, and on a phone, 375 × 812, where each problem is a card; with the message of a failed save, a token that Paperless refuses; with the URL of another server, for which the token field is required; and with the message after saving. The last three show the empty history that *Clear history* leaves. Then it checks the section *Paperless* of the personal settings, `#paperless-unified-search-personal`, on a laptop with the message after ticking *Always search my Paperless documents*, which it unticks again, and on a phone, where the checkbox stays in front of its label and the section within the width of the screen. It signs in through the login form and looks only into the element of the app on each page, `#paperless-unified-search-settings` or `#paperless-unified-search-personal`, the element that holds the markup of `templates/`, `js/` and `css/`, so that what Nextcloud draws around it doesn't count. A serious or critical violation fails the suite; the others are listed in the log.

On the way to these states, the script checks what the settings page does in the browser, and a state that differs fails the suite too. The token field asks for the token again for another scheme, host or port, but not for another path of the stored server. Saving another server with its token makes it the stored URL, after which the mock's own name is the other server; and an archive account that exists ends the warning. The message after each save has the colour that the theme of Nextcloud has for its kind, success or error, and an icon in front, so that the kind doesn't rest on the colour alone; the fields of text are as wide as each other and each checkbox, at least 20 pixels big, stands in front of its label. On the phone, nothing is wider than the screen, and no text runs out of the cell of its table. After the state on the phone, in both themes, *Clear history* empties *Search problems* at once and says *History cleared.*, on the same page, which saves loading it once more. `run.sh` then checks that the settings are stored as the browser saved them, and that the page that Nextcloud renders shows no problem any more.

The results in the global search of Nextcloud are left out: Nextcloud draws them, and the app only gives the title, the line below it and the icon. axe-core does find a serious violation there, *nested-interactive*, but every search provider has it, because Nextcloud puts the link of each result into an option of a list box; only Nextcloud can fix it. [The search dialog](#the-search-dialog) checks what the results show instead.

The browser runs in the image of Playwright that `run.sh` names, inside the network of the Compose project, and reaches Nextcloud as `http://nextcloud`; the suite turns off the first-run wizard of Nextcloud, which would cover the pages. `package.json` and `package-lock.json` pin axe-core and playwright-core. Keep playwright-core at the version of the image: Renovate updates both together (`.github/renovate.json5`), and `scripts/check-project.sh` compares them.

## The messages of the settings page

Last, `settings.mjs` checks what the settings page says and does when an answer isn't the one that it asked for, and *Disconnect*, which the other checks leave alone. It runs last, as it disconnects Paperless, and saves the settings again as `run.sh` expects them afterwards. First it tries a search for `mobiletest` as `e2e-user` with *Try a search* and expects document 123 shown, with its tag, and 999 without a file, with their titles as text. Then:

1. A save answered with the HTML page of maintenance mode, the page of a proxy whose Nextcloud doesn't answer (HTTP 504), an expired session (401), a request token that Nextcloud no longer accepts (412) and a network failure each shows one short sentence in the colour of an error, and the settings stay as they are. Playwright gives these answers, which Nextcloud itself would give only during an upgrade or after the session ended.
2. *Disconnect*, declined in the dialog of the browser, sends nothing and changes nothing; confirmed, it empties the form and the history, turns itself off, and Nextcloud renders the page of a fresh install.
3. A first save that Paperless refuses keeps *Disconnect* off, as nothing is stored to disconnect, and keeps the URL that was typed for its correction.
4. A save with the right token shows the URL as Nextcloud stored it, without the slash at its end, and turns *Disconnect* on.

`tests/js/settings.test.mjs` checks the same script without a browser, for every answer and every branch of it, in `scripts/check.sh`.

## The search dialog

After the accessibility check, in the same container, `flow.mjs` goes through the search of Nextcloud as a person does, on a laptop, 1280 × 800 pixels, and then on a phone, 375 × 812, or at the sizes that `E2E_FLOW_SIZES` names, such as `laptop`, which a pull request sets for every version but the newest ([In the CI](#in-the-ci)); it notes a size that it leaves out in the log, and fails on a name that isn't one of its sizes, a choice of `sizes.mjs` that `tests/js/sizes.test.mjs` tests without a browser: signed in as `e2e-user`, it opens its personal settings and the search in their header, waits until the search can search, types `mobiletest`, adds the connected services and expects the group *Paperless documents* with only the result *Mobile viewer test*, without the document that no file stands for. A screen reader reads the result as its title, then the date of the document, its correspondent, its type and its excerpt as text, `O'Brien & "Sons" < GmbH>` from the tags and entities of Paperless. A click on the result opens the file in Files, in the Viewer, which names it in its header; the file is a real PDF that `pdf.py` writes, which the Viewer draws, but the check doesn't wait for that, which is Nextcloud's own job and takes Chromium seconds. ## The coming Nextcloud

Every Monday, and when started by hand, the workflow also runs the suite against the coming Nextcloud:

```bash
bash tests/e2e/canary.sh
```

The coming Nextcloud is the newest beta or release candidate of the next major version while Nextcloud publishes one, in `https://download.nextcloud.com/server/prereleases/`, and otherwise the daily build of its master branch, `https://download.nextcloud.com/server/daily/latest-master.tar.bz2`. Nextcloud no longer publishes Docker images of betas and release candidates, so the script checks the signature of the package against the release key of Nextcloud, as the official image does, and puts its code into the image of the newest release, `nextcloud:apache`, which keeps its PHP, Apache and start script. The suite enables the app with `--force`, as `max-version` of `appinfo/info.xml` doesn't name that version yet; the upstream bot raises `max-version` once Nextcloud releases the version.

The canary is no required check and blocks nothing. When it fails, it opens the issue *The coming Nextcloud breaks the app* with a link to the run, adds every further failed run to it, and closes it once the tests pass again.

Optional environment variables, besides those of `run.sh`:

- `CANARY_BASE_IMAGE`: the image whose code the coming Nextcloud replaces, default `nextcloud:apache`
- `CANARY_IMAGE`: the local image the script builds, default `paperless-unified-search-e2e:coming`

`paperless-contract.sh` adds `compose.paperless.yaml` to `compose.yaml` and starts the Paperless of the line by its profile, `paperless-2` or `paperless-3`, with Redis, beside Nextcloud and the mock; Paperless answers as `paperless` in the network of the project. That script gets a token of the API for the synthetic administrator, gives Paperless the three text files of `contract/documents/` with a title and a date each, waits until Paperless has read and indexed them, and checks what the app relies on, with the header `Accept` and the fields of a result that the app sends, which the script reads from the constants `ACCEPT`, `SEARCH_FIELDS` and `RECENT_FIELDS` of `lib/Service/PaperlessApiService.php`:

- the headers `X-Version` and `X-Api-Version`, which the settings show, and the version of the line;
- the fields of a result: only those that the app asks for, `id` a number, `title` a text, `created` a date `YYYY-MM-DD`, `correspondent` and `document_type` an ID or null, `tags` a list of IDs, and `__search_hit__` with its `highlights` as text;
- the pages of a search: `next` links the next page and is null on the last, and a page past it answers HTTP 404;
- the excerpt: Paperless marks the term, with `<b>` in Paperless-ngx 3 and `<span class="match term0">` in Paperless-ngx 2, and writes the characters of HTML as entities; the text that the app makes of it keeps the term and neither markup nor an entity;
- the filters `created__date__gte` and `created__date__lte`;
- the newest documents, as the widget of the dashboard asks for them, `ordering=-added` with the fields of `RECENT_FIELDS`: only those fields, the newest first, and `added` a moment with its time;
- the names of correspondents, document types and tags, as the app asks for them with the IDs of the results, `id__in` and as many on a page (`PaperlessNames`): one page with the `id` as a number and the `name` as a text of each object asked for, and of a tag `is_inbox_tag` as a boolean, true for the tag of the inbox alone, without a second one that nobody asked for and without an ID that Paperless doesn't know; an answer of another shape, a field `name` that Paperless renames or an `id__in` that it ignores fails the contract;
- what `/api/ui_settings/` says an account may do: the superuser, an account that the script adds with the permissions to view that the documentation recommends, and one without the permission to view its UI settings, which Paperless refuses with HTTP 403;
- a query that is still being typed, `invoice created:[2026 to`: Paperless-ngx 3 refuses it with HTTP 400 and the errors of `query`, and its simple mode, `text=`, finds the documents of a term; Paperless-ngx 2 answers it;
- through Nextcloud: the test of the connection in the settings names the same versions, the search finds the documents of the files `<title> [P<ID>].txt` of the archive account with the excerpt as text, the unfinished query fails no search, and the settings save the token of the account with the recommended permissions without a warning and that of the superuser with the warning `superuser`;
- what each permission of the account of the token gives the search, as the table *What each permission gives the search* of `docs/configure.md` says: without the permission to view documents, Paperless refuses the token with HTTP 403; with it, an account finds a document of another owner only once it may view it; without the permission to view correspondents, document types or tags, Paperless refuses their names with HTTP 403, and with it, it names only those that the account may view, so not those of the superuser until the account may view them, and then Nextcloud's results show them, without the tag of the inbox; a search of the notes, `notes:remittance`, sends the words of the note without the permission to view notes; and a workflow with the trigger *Document Added* and an action *Assignment* lets the account view a new document, `contract/documents/contract-receipt.txt`, which the script deletes again with the workflow. In between, the settings warn with `hides_names_of_others` about the correspondent, the type and the tag that the account can't see yet, and no longer once it may.

The summary of the job shows the versions, every check and what Paperless sent, and the first check that fails names the promise that Paperless or the app breaks. A version of the API that Paperless no longer accepts, a field that Paperless leaves out or the markup of an excerpt that reaches the result fails the tests.

The job runs every Monday, when started by hand, and in a pull request that changes the app, `appinfo/` or `lib/`, whose search, names, dashboard, settings and commands of occ all talk to Paperless or read its answers, the mock `mock_server.py`, in whose container the assertions run, the files of the contract tests or the workflow. `scope.sh` with `SCOPE=paperless` decides it, as it does for the check `nextcloud`. Its jobs `paperless (2)` and `paperless (3)` are required checks, so a pull request that breaks the contract can't merge, by auto-merge neither; one that changes no file that they cover passes them in seconds, and with about two minutes they end before the check `nextcloud` beside them. A failed run on Monday opens the issue *Paperless-ngx breaks the app* with a link to the run, adds every further failed run to it, and closes it once the tests pass again. Renovate keeps the images of `compose.paperless.yaml` current by their digests, the one of Paperless-ngx 2 within version 2, so every new release of Paperless-ngx arrives as a pull request of its own, apart from the other images, that runs the contract against it. Renovate merges it itself only once every check passed, also those that aren't required, such as the demo, which runs the same Paperless-ngx 3.

Optional environment variables, besides `DOCKER_BIN` and `KEEP_E2E` of `run.sh`:

- `PAPERLESS`: the line of Paperless-ngx, `2` or `3`, default `3`
- `E2E_PORT`: host port for Nextcloud, default `18092` or `18093`, so that `run.sh` can run at the same time
- `E2E_PROJECT_NAME`: Compose project name, default `paperless_unified_search_contract_<line>`
